# 原购买 1min=241 与新 QMT 月增量=240：真实证据及只读核对（2026-11-28）

## 1. 已经由用户 Windows 真实数据验证的事实

从 PR #295 已固定 HEAD `b69aae6132c5eb5fa719f94ffb7098d2dcf408f3` 的用户实机日志：

- 单 GUI 启动器契约 5/5、原更新中心 11/11、原购买 1m 根数审计 10/10 全部测试通过。
- **唯一被直接审计的购买原件**：`D:\stock\AllCycleAStockData\1min\2026-09.parquet`，仅 **2026-09-30** 日。5,650 个股票日、总 1,361,650 行，**全部每股 241 行**；240 行股票日=0，其他行数=0，重复证券时间戳=0；最早本地 09:30，最晚 15:00；所有 5,650 股都有 09:30、09:31 两条独立时间标签。09:30 量、额同为正 5,456，双零 194，数量不匹配 0。整月文件 Footer 的 28,547,414 行不是上述单日行数。
- 该审计没有读取 QMT 原生、H5 或新增 2026-10/11 月文件；**不能声称所有历史年份都必然 241，也不能声称之前生成的 10/11 月已经过此检查**。
- 09:30 有实际量额的记录意味着购买库没有整体剔除该标签，**但不能仅凭 09:30 K 线判断 09:15–09:25 集合竞价的所有成交、委托、撤单或盘前深度数据已保留**。还需校验原供应商时间归属、成交额日汇总、有效的不同来源及可能的逐笔数据。

## 2. 当前代码确有 241/240 业务兼容性冲突

`market_month_storage._fold_241_day` 实现原 QMT 241→240：09:30 双零就移除，09:30 双正就量额及 OHLC 归入 09:31。虽然强调日线量额守恒，但函数注释错误地写“购买 1m 格式是 240 个标签”。`update_market.normal_qmt_day` 和每日 `stage_day` 的行数/时间格点门槛也均是 240，后续 `market_derived_cycles.aggregate_stock_day` 使用 240 作为基础分钟输入。这与已验收的实际原购买 2026-09-30 241 根事实在**时间标签与粒度层面直接不一致**。

这里必须区分：

- **不等于**已经证明 240 根 QMT 新增记录的 OHLC、全日成交量或成交额出错：原有折叠转换设计刻意守恒。
- **也绝不等于**已经证明历史 241/新增 240 两种分钟库在任何分钟时间键或集合竞价成交口径上兼容；它们已不是同一种逐分钟行数的直接契约。
- 第三个层次是已经入库的新月文件到底采用多少根；只有重新扫描其真实物理文件和现有 ledger 才能确认，不能拿目标代码乘法当成已发生的写入。

## 3. 新增的独立两文件、两交易日只读诊断

`audit_incremental_vs_purchased_minute_count_readonly.py` 只调用此前已验收的本机 Parquet 行数/09:30 只读观察器，核对某个原购买月份和另一个已生成月份**实际存在**的文件，报告每股根数分布、09:30 是否普遍保留、09:30 量额双正的数量及是否出现重复分钟主键。

示例从 Windows 原购买 **2026-09-30** 与现存新月 **2026-11-12** 对比：

```powershell
& 'D:\ChatGPT\AStockDataTools\.venv\Scripts\python.exe' -B '.\audit_incremental_vs_purchased_minute_count_readonly.py' --purchased-file 'D:\stock\AllCycleAStockData\1min\2026-09.parquet' --purchased-day 2026-09-30 --expected-reference-stocks 5650 --incremental-file 'D:\stock\AllCycleAStockData\1min\2026-11.parquet' --incremental-day 2026-11-12
```

运行目录必须为本功能的独立测试 worktree 下 `ParquetLiveSync`。程序不下载、不补零、不写数据、不自动纠正文件，不会读取 QMT/H5、不操作任务计划程序。无购入源原文件内容 SHA 验证权，不冒充加密 provenance。

如果目标文件不存在、目标日没有行、出现重复键或原购买锚股票日数不是 5650，则**按错误退出**，不能因为查不到结果就认为“新库是 240 根”。如果实际新库每股 240 行而参考每天都是 241，明确返回 `PAID_241_VS_INCREMENTAL_BAR_GRID_CONFLICT_REVIEW_REQUIRED` 且 `bar_count_and_opening_label_profile_match=false`。如果数量和首根标签都吻合，也仅返回形态匹配、不认证业务成交归属或竞价真实性；没有生产写入权限。

## 4. 修复策略：先观察再设计，而不是重新套用 240

1. 保存购买原文件 2011–2026 的原始 SHA/版本；固定 2026-09 原支付基准以及 2026-10/11 已产生的新月文件的 SHA/交易日回执；对高于一日的多个交易日、跨市场、含停牌/零成交的边界样本继续做只读多日复核。
2. 分别对 QMT 原生 241 与购买原始 241 样本的 **09:30 与 09:31 逐字段**核对，证明时标、成交量单位、成交额单位、开高低收以及日聚合口径。先不用 240 折叠结果推断来源 241 含义。09:30 双零样本也不能根据零量额就称来源是伪造行情。
3. 如证据支持采用购买库 241 结构，开发单独版本的新 241 标准化器、全部八周期所需的新聚合规则及对应正反样本；只在隔离私有候选目录创建版本，不覆盖已购原文件、旧 240 月文件或原 QMT 收据。继续对每日公开源 DAY 执行六字段校验与双 SHA，并新增 241 与高周期换算场景回归。
4. 对已有的 2026-10/11 各真实已提交月份，经过旧文件备份、来源证据固定、候选逐字段对照和单独审批，才能考虑新月版本切换。不能为了统一行数制造虚假的 09:30 K 线，更不能把 240/241 任意一种强行标记为“已完全校准”。
5. 在第 2–4 步完成之前，新增市场数据写入必须明确标记 `PURCHASED_241_QMT_240_GRID_SEMANTIC_REVIEW_REQUIRED`，而不是声称 240 `purchased-compatible`。原主线 Draft 状态及金融 76+1 pending、九条市场隔离均不受影响。

本阶段纯证据诊断：新增 **7 项**合成 Parquet 测试，真实 Windows 的新增 7 项及本机新月对照在实际回执返回前**均未验收**。源代码、文档/合成测试可放 GitHub；真实付费数据仍留 Windows 本地。
